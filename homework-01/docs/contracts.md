# Контракты взаимодействия

Для каждого сервиса ниже указаны запросы, команды, события и зависимости. Запросы читают данные, команды меняют их или запускают действие. В разделе событий перечислено то, что сервис публикует; входящие события указаны в зависимостях.

## Сервис "Точки продаж"

**Название:**

Stores. Точки продаж. Настройки точек, франшизы, часы работы и доставка.

**Запросы:**

- `GET /v1/stores?country=...`
  Вызывает: UI через Gateway.
  Данные запроса: Страна, необязательные координаты.
  Ответ: `200`: точки, адреса, часы, timezone, способы получения и оплаты.

- `POST /v1/stores/{storeId}/eligibility`
  Вызывает: Orders.
  Данные запроса: `fulfillmentType, deliveryAddress?`.
  Ответ: `200`: `eligible, reason?, country, timezone, currency, paymentMethods, deliveryFee, configVersion`; самовывоз имеет нулевой тариф.

**Команды:**

- `PATCH /v1/stores/{storeId}`
  Вызывает: Владелец через Gateway.
  Данные запроса: `expectedVersion, hours?, deliveryZone?, deliveryFee?, paymentMethods?`.
  Ответ: `200`: новая версия; только своя точка.

**События:**

- Не публикует события в текущем варианте.

**Зависимости:**

- Бизнес-данные других сервисов не запрашивает. Его API используют Orders и сайт.

**Вопросы:**

- Кто задает зоны и стоимость доставки: сеть или владелец точки?

## Сервис "Меню и акции"

**Название:**

Menu. Меню и акции. Блюда, цены, доступность и расчет скидок.

**Запросы:**

- `GET /v1/stores/{storeId}/menu`
  Вызывает: UI через Gateway.
  Данные запроса: Точка.
  Ответ: `200`: блюда, доступность, цены, действующие акции.

**Команды:**

- `POST /v1/quotes`
  Вызывает: Orders.
  Данные запроса: `storeId, country, timezone, items[{productId, quantity}]`.
  Ответ: `201`: `menuQuoteId, lines, discountBreakdown, subtotal, expiresAt, menuVersion`; недоступное блюдо - `422`.

- `PATCH /v1/stores/{storeId}/menu/{productId}`
  Вызывает: Владелец через Gateway.
  Данные запроса: `expectedVersion, price?, available?`.
  Ответ: `200`: новая версия; только своя точка.

- `POST /v1/promotions`
  Вызывает: Менеджер/владелец через Gateway.
  Данные запроса: `scope=NATIONAL/LOCAL, country, storeId?, startsAt, endsAt, productIds, discountPercent`.
  Ответ: `201`: `promotionId`; национальная акция - право менеджера, локальная - владельца точки.

**События:**

- Не публикует события в текущем варианте.

**Зависимости:**

- Получает страну и часовой пояс точки от Orders. Orders предварительно запрашивает их в Stores. На события других сервисов пока не подписан.

**Вопросы:**

- Нужно ли разрешать совместное применение скидок сети и точки? Пока выбирается самая большая скидка.

## Сервис "Заказы"

**Название:**

Orders. Заказы. Оформление заказа, его статус, запуск оплаты и контроль выполнения.

**Запросы:**

- `GET /v1/orders/{orderId}`
  Вызывает: UI через Gateway.
  Данные запроса: Токен доступа покупателя или токен персонала.
  Ответ: `200`: состав, итоговая цена, статус, `readyAt?, deliveryEta?, paymentStatus, paymentUrl?`.

**Команды:**

- `POST /v1/checkout-quotes`
  Вызывает: UI через Gateway.
  Данные запроса: `storeId, items, fulfillmentType, deliveryAddress?, paymentMethod`.
  Ответ: `201`: `quoteId, lines, deliveryFee, total, expiresAt`; Orders сохраняет полный расчет на основе Stores и Menu.

- `POST /v1/orders`
  Вызывает: UI через Gateway.
  Данные запроса: `quoteId, customerContact, source=WEB`.
  Ответ: `201`: `orderId, status=PENDING_ACCEPTANCE, accessToken`; просроченный расчет - `409`, клиент запрашивает новый и подтверждает измененную цену.

- `POST /v1/orders`
  Вызывает: Сотрудник через Gateway.
  Данные запроса: Те же поля, `source=FAX`.
  Ответ: `201`: заказ той же очереди; право создавать `FAX` есть только у сотрудника точки.

- `POST /v1/orders/{orderId}/collection`
  Вызывает: Сотрудник через Gateway.
  Данные запроса: `method=IN_STORE/COD, receiptReference`.
  Ответ: `202`: запрос на регистрацию оплаты принят; Orders проверяет состояние, сохраняет команду RecordCollection в outbox и возвращает ответ.

**События:**

- `OrderPlaced` { `orderId, storeId, items, fulfillmentType, paymentMethod, deliveryAddress?, customerContact` }
  Получатель: Fulfillment. Создать одно задание на заказ.

- `PreparationAuthorized` { `orderId` }
  Получатель: Fulfillment. Разрешить приготовление принятого заказа.

- `HandoverAuthorized` { `orderId, paymentId` }
  Получатель: Fulfillment. Разрешить выдачу после готовности.

- `OrderCancelled` { `orderId, reason` }
  Получатель: Fulfillment. Прекратить исполнение и освободить резерв, не возобновлять по запоздавшему разрешению.

**Зависимости:**

- Запрашивает параметры точки в Stores и стоимость блюд в Menu по HTTPS.
- Отправляет в Payments через Kafka команды `CreatePayment`, `RecordCollection`, `RefundPayment`.
- Слушает от Payments `PaymentCreated`, `PaymentCommandRejected`, `PaymentSucceeded`, `PaymentFailed`, `PaymentRefunded`.
- Слушает от Fulfillment `FulfillmentAccepted`, `FulfillmentRejected`, `FulfillmentUpdated`, `AwaitingPickup`, `AwaitingDelivery`, `OrderReceived`, `FulfillmentFailed`.

**Вопросы:**

- Сколько ждать подтверждения точки и оплаты? В каких случаях покупатель может отменить заказ?

## Сервис "Исполнение заказа"

**Название:**

Fulfillment. Исполнение заказа. Очередь кухни, время готовности, самовывоз и доставка.

**Запросы:**

- `GET /v1/tasks?storeId=...`
  Вызывает: Сотрудник через Gateway.
  Данные запроса: Точка.
  Ответ: `200`: очередь заданий с текущими версиями.

- `POST /v1/routes`
  Вызывает: UI через Gateway.
  Данные запроса: `origin, destination, mode`.
  Ответ: `200`: `provider, directionsUrl, durationSeconds?, trafficAvailable`; при недоступности провайдеров - адрес назначения и `trafficAvailable=false`.

**Команды:**

- `POST /v1/tasks/{taskId}/transitions`
  Вызывает: Сотрудник/водитель через Gateway.
  Данные запроса: `action, expectedVersion, readyAt?, driverId?, deliveryEta?, reason?`.
  Ответ: `200`: новое состояние и версия; действия `ACCEPT/REJECT/START/READY/ASSIGN_DRIVER/DISPATCH/COMPLETE/FAIL`; недопустимый переход - `409`.

**События:**

- `FulfillmentAccepted` { `orderId, storeId, taskId, readyAt, reservationExpiresAt` }
  Получатель: Orders. Сохранить время; начать оплату либо разрешить приготовление.

- `FulfillmentRejected` { `orderId, reason` }
  Получатель: Orders. Отклонить заказ без оплаты.

- `FulfillmentUpdated` { `orderId, status, readyAt, deliveryEta?, driverId?` }
  Получатель: Orders. Обновить промежуточный статус или ожидаемое время. При начале приготовления передается `PREPARING`, при отправке доставщика - `DISPATCHED`. Это событие не завершает заказ и не заменяет события готовности ниже.

- `AwaitingPickup` { `orderId, storeId, taskId, readyAt` }
  Получатель: Orders. Заказ готов к самовывозу. Показать статус `AWAITING_PICKUP`.

- `AwaitingDelivery` { `orderId, storeId, taskId, readyAt, driverId, deliveryEta?` }
  Получатель: Orders. Заказ готов и доставщик назначен. Показать статус `AWAITING_DELIVERY`. Отправка доставщика отмечается отдельно через `FulfillmentUpdated` со статусом `DISPATCHED`.

- `OrderReceived` { `orderId, storeId, taskId, fulfillmentType, receivedAt` }
  Получатель: Orders. Заказ передан покупателю. Установить статус `COMPLETED`.

- `FulfillmentFailed` { `orderId, reason` }
  Получатель: Orders. Отменить исполнение, при наличии оплаты запросить возврат.

**Зависимости:**

- Слушает от Orders `OrderPlaced`, `PreparationAuthorized`, `HandoverAuthorized`, `OrderCancelled` через Kafka.
- Запрашивает маршрут и время в пути у картографических провайдеров A и B по HTTPS.

**Вопросы:**

- Кто и как меняет время доставки при задержке? Как поступать, если свободного доставщика нет?

## Сервис "Платежи"

**Название:**

Payments. Платежи. Онлайн-оплата, запись оплаты при получении и возврат денег.

**Запросы:**

- Нет отдельных запросов на чтение. Результаты оплаты передаются в Orders через Kafka.

**Команды:**

- `CreatePayment` через Kafka от Orders.
  Данные: ``orderId, storeId, total, method=ONLINE, expiresAt``.
  Результат: `PaymentCreated` со ссылкой на оплату или `PaymentCommandRejected`.

- `RecordCollection` через Kafka от Orders.
  Данные: ``orderId, storeId, total, method=IN_STORE/COD, receiptReference, actorId``.
  Результат: `PaymentSucceeded` после записи полученных денег или `PaymentCommandRejected`.

- `RefundPayment` через Kafka от Orders.
  Данные: ``orderId, paymentId, reason``.
  Результат: `PaymentRefunded` после подтверждения полного возврата или `PaymentCommandRejected`; сумму берет Payments из исходного платежа.


**События:**

- `PaymentCreated` { `orderId, paymentId, paymentUrl, expiresAt` }
  Получатель: Orders. Сохранить ссылку и показать ее покупателю, если заказ еще ожидает оплату.

- `PaymentCommandRejected` { `orderId, commandId, commandType, reason` }
  Получатель: Orders. Показать ошибку операции; для возврата оставить `REFUND_PENDING`.

- `PaymentSucceeded` { `orderId, paymentId, total, method, paidAt` }
  Получатель: Orders. Сверить сумму и заказ; разрешить приготовление и выдачу, либо вернуть позднюю оплату отмененного заказа.

- `PaymentFailed` { `orderId, paymentId, attemptId, reason` }
  Получатель: Orders. Показать ошибку; новая попытка допустима до истечения резерва.

- `PaymentRefunded` { `orderId, paymentId, refundId, total` }
  Получатель: Orders. Установить статус возврата `REFUNDED`.

**Зависимости:**

- Получает команды от Orders из Kafka. Прямых HTTP-вызовов между Orders и Payments нет.
- Вызывает API платежного провайдера по HTTPS, получает ID платежа и ссылку на оплату.
- Получает от провайдера webhook с результатом оплаты или возврата. Проверяет подпись, сумму и валюту. Повторные уведомления не обрабатывает заново. Данные карты остаются у провайдера.

**Вопросы:**

- Какого платежного провайдера использовать? Как распределяются деньги между сетью и владельцами точек?

## Общие правила

- Синхронные запросы: HTTPS, JSON, префикс `/v1`. Идентификаторы - UUID, время - ISO 8601 UTC, деньги - `{amountMinor: integer, currency: string}`.
- Команды создания используют `Idempotency-Key`. Повтор ключа с тем же телом возвращает прежний результат, с другим телом - `409`. Ключ сохраняется в БД вместе с результатом.
- Ошибки: `{code, message, correlationId}`. HTTP `400` - неверный формат, `401/403` - доступ, `404` - объект отсутствует, `409` - конфликт состояния/цены, `422` - бизнес-ограничение, `503` - временно недоступная зависимость.
- Сервисы проверяют идентичность вызывающего и права. `storeId` из запроса не доказывает право доступа. Персонал ограничен своими точками, менеджер сети - разрешенными странами. Покупатель читает заказ по защищенному непрогнозируемому токену.
- Цена и разрешенные способы оплаты рассчитываются сервером. Клиент не задает итоговую сумму платежа или платежный аккаунт.
- Для чтений и идемпотентных команд допустимы ограниченные повторы с задержкой. Таймаут команды означает неизвестный результат: сначала повтор с тем же ключом или проверка состояния, а не создание нового объекта.

## Расчет цены и выдача заказа

Menu определяет период акции по часовому поясу точки, полученному Orders из Stores по доверенному каналу. `expiresAt` расчета не выходит за конец примененной акции. Orders гарантирует цену полного расчета до `expiresAt`; после создания заказа сохраняет ее снимок. Изменение доступности после расчета может привести к отказу точки, но не к молчаливой замене состава или суммы.

`START` возможен только после `PreparationAuthorized`, `COMPLETE` - после `HandoverAuthorized`; доставка дополнительно требует назначенного водителя и состояния `DISPATCHED`. `FAIL` публикует отказ исполнения и передает ошибку в Orders для отмены и возврата денег. Изменение задания и его событие сохраняются одной транзакцией.

Для самовывоза действие `READY` публикует `AwaitingPickup`. Для доставки `AwaitingDelivery` публикуется, когда выполнены оба условия: заказ готов и доставщик назначен. Порядок действий `READY` и `ASSIGN_DRIVER` может быть любым. До этого готовность видна в очереди Fulfillment. Действие `DISPATCH` требует готового заказа и назначенного доставщика. `COMPLETE` выполняется после передачи заказа покупателю и публикует только `OrderReceived`, без отдельного `FulfillmentUpdated COMPLETED`. Для самовывоза перед `COMPLETE` также проверяется готовность заказа.

## Обработка сообщений Kafka

Orders отправляет задания на оплату в топик `payments.commands`, Payments отвечает через `payments.events`. Ключ сообщения в обоих топиках - `orderId`. Команды читает группа `payments`, результаты читает группа `orders`. Права на запись команд есть только у Orders. HTTP между Orders и Payments не используется. Payments обращается к внешнему платежному провайдеру по HTTPS.

У команды есть `commandId`, `commandType`, `schemaVersion`, `occurredAt`, `correlationId` и `payload`. В `payload` всегда передается `orderId`. `commandId` создается один раз на операцию и не меняется при повторе. В ответных событиях передается `causationId` с ID команды, для которой получен результат.

После отправки `CreatePayment` Orders показывает `paymentStatus=CREATING`, без ссылки на оплату. Payments создает платеж у провайдера, сохраняет его и отправляет `PaymentCreated`. Orders сохраняет `paymentUrl` и статус `PENDING`. Сайт периодически запрашивает `GET /v1/orders/{orderId}` и показывает ссылку, когда она появилась. Если заказ уже отменен или срок вышел, ссылка не показывается. Позднее списание возвращается покупателю.

`POST /v1/orders/{orderId}/collection` возвращает `202` после сохранения команды, не дожидаясь Payments. До `PaymentSucceeded` оплата считается неподтвержденной и выдача не завершается. Повтор HTTP-запроса с тем же `Idempotency-Key` возвращает прежний результат и не создает новую команду.

Payments не создает платеж по просроченной `CreatePayment`. Для одного заказа допускается один активный онлайн-платеж. Повтор команды не создает второе списание, запись оплаты или возврат. Payments сначала сохраняет операцию в своей БД, затем обращается к провайдеру с постоянным ключом операции. Если сервис перезапустился после внешнего вызова, он проверяет результат или повторяет вызов с тем же ключом.

Временные ошибки повторяются с задержкой. Если запрос отклонен окончательно, Payments отправляет `PaymentCommandRejected`. Orders показывает ошибку создания платежа или учета оплаты; при ошибке возврата оставляет `REFUND_PENDING` для разбора сотрудником. Неизвестный результат внешней операции сначала проверяется у провайдера. Задержка Kafka не означает, что платеж не прошел.

У всех событий одинаковые служебные поля.

Команды и события могут прийти несколько раз (at least once). Сервис записывает сообщение в outbox в той же транзакции, что и изменения заказа или платежа, затем отправляет в Kafka. Получатель сохраняет `commandId` или `eventId` в inbox вместе с результатом обработки. Если такой ID уже есть, действие не повторяется. Прочитанная позиция в Kafka подтверждается после записи в БД. У каждого сервиса своя группа потребителей. После нескольких неудачных попыток сообщение попадает в отдельный топик ошибок (DLQ), где его можно разобрать. Outbox, задержки обработки и DLQ требуют контроля, чтобы команды не оставались без обработки.

`aggregateVersion` задает порядок изменений одного объекта в одном сервисе. Версии из разных сервисов между собой не сравниваются. Если пропущено сообщение, обработка ждет его восстановления. Старое сообщение не должно менять статус обратно. Orders и Fulfillment проверяют, можно ли выполнить действие в текущем статусе. Отмененный заказ не запускается заново. Даже если отмена пришла раньше `OrderPlaced`, Fulfillment запоминает ее и не создает активное задание позже.

Orders хранит срок оплаты в БД и проверяет его в фоне, в том числе после перезапуска. Если оплата пришла после отмены, запускается возврат. Если платеж создан, но ответ потерялся, запрос повторяется с тем же ключом. Когда результат неизвестен, Payments сначала запрашивает его у платежного провайдера.

Контактные данные и адрес доступны только тем, кто выполняет заказ. Их не нужно добавлять в общие журналы. Читать `OrderPlaced` из Kafka может только Fulfillment.

Если один сервис карт не отвечает, Fulfillment обращается ко второму. Если данные о пробках получить не удалось, ответ содержит `trafficAvailable=false`. Покупатель видит адрес назначения без обещания точного времени в пути.
